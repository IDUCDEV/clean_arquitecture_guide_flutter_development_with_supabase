# di-getit-scaffold — Scaffold de inyección de dependencias con GetIt

Mantiene el módulo de inyección de dependencias de GetIt. Ordena por capa: external → core → datasources → repositories → usecases → cubits.

> **Orquestación:** esta skill suele invocarse desde `clean-arch-feature` cuando el usuario pide `wiring: [di]`. En ese flujo, los componentes generados (datasources, repositorios, usecases, cubit, estado) llegan **ya anotados** por los templates de `clean-arch-feature` / `clean-arch-component`; la skill solo los verifica y añade lo externo que falte. Puede usarse también de forma independiente sobre un feature ya existente.

> **¿`injectable` o `manual`?** El modo por defecto es `injectable` — el del prompt `PROMPT-BOOTSTRAP-MONOREPO.md` (v2): cada clase se anota donde vive y `make gen` escribe el registro. El modo `manual` es **legacy / brownfield**: solo para proyectos que ya tienen la cascada manual en `service_locator.dart` (v1) y aún no migraron, como el monorepo real. Para proyectos nuevos usa `injectable`.

## Input requerido

| Parámetro | Descripción | Ejemplo |
|---|---|---|
| `mode` | Estilo de DI. **Default: `injectable`** | `injectable` o `manual` |
| `app_name` | Nombre del paquete | `my_app` |
| `features` | Lista de features con sus dependencias | (ver tabla abajo) |
| `external_libs` | Librerías externas que el feature necesita | `SupabaseClient`, `Isar`, `InternetConnection`, `http.Client` |

> En modo `injectable`, "registrar" una librería externa = asegurar su getter en `external_module.dart`. En modo `manual`, `SupabaseClient` **no** se registra (los datasources reciben `Supabase.instance.client` directo).

### Formato de `features`

Cada feature puede incluir:

```yaml
feature: product
external_datasources: [SupabaseClient]
remote_datasource: ProductRemoteDataSource
local_datasource: ProductLocalDataSource  # opcional
repository: ProductRepository
repository_impl: ProductRepositoryImpl
usecases: [GetProducts, GetProduct, CreateProduct, UpdateProduct, DeleteProduct]
cubit: ProductCubit
```

## Output — Modo `injectable` (default, recomendado)

El registro **no se escribe a mano**: cada clase se anota donde vive y `make gen` genera `service_locator.config.dart`. El directorio `core/di/` tiene dos archivos manuales y ninguno contiene registros.

**`lib/core/di/service_locator.dart`** — solo declara `sl` y `configureDependencies()`:

```dart
import 'package:get_it/get_it.dart';
import 'package:injectable/injectable.dart';

import 'package:{app_name}/core/di/service_locator.config.dart';

/// El contenedor de dependencias. Todo el proyecto usa `sl`.
final GetIt sl = GetIt.instance;

/// No escribas el registro a mano: anota cada clase donde vive (ver tabla
/// abajo) y `make gen` escribe el cuerpo en `service_locator.config.dart`.
@InjectableInit(
  initializerName: 'init',
  // `false` = el config generado usa imports `package:` como todo `lib/`.
  preferRelativeImports: false,
)
Future<void> configureDependencies() async {
  // Isar arranca dentro del `@module` (@preResolve); `init()` lo espera.
  await sl.init();
}
```

**`lib/core/di/external_module.dart`** — lo que no se puede anotar (clases de terceros):

```dart
import 'package:http/http.dart' as http;
import 'package:injectable/injectable.dart';
import 'package:internet_connection_checker_plus/internet_connection_checker_plus.dart';
import 'package:isar_community/isar.dart';
import 'package:supabase_flutter/supabase_flutter.dart';

import 'package:{app_name}/core/data/local/isar_service.dart';

/// Dependencias de terceros. Un `@module` es la traduccion de un
/// `registerLazySingleton` manual, declarado al lado del resto de la DI.
///
/// `SupabaseClient` no crea un cliente nuevo: devuelve la misma instancia de
/// la libreria (`Supabase.instance.client`); GetIt guarda la referencia para
/// inyectarla por tipo. El getter no se ejecuta hasta que `main()` llama a
/// `Supabase.initialize()` antes de `configureDependencies()`.
@module
abstract class ExternalModule {
  /// El unico init asincrono de la app. `@preResolve` hace que `init()`
  /// espere este Future antes de registrar el resto.
  @preResolve
  Future<Isar> get isar async {
    await IsarService.initialize();
    return IsarService.instance;
  }

  @lazySingleton
  InternetConnection get internetConnection =>
      InternetConnection.createInstance();

  @lazySingleton
  http.Client get httpClient => http.Client();

  @lazySingleton
  SupabaseClient get supabaseClient => Supabase.instance.client;
}
```

> `InternetConnection.createInstance()` (no `newInstance`): es el constructor de fabrica real de `internet_connection_checker_plus` 2.9.1+2.

**Anotaciones requeridas** (el template de cada clase ya las emite; si faltan, la skill las añade):

| Capa | Anotación | Regla |
|---|---|---|
| DataSource (impl) | `@LazySingleton(as: ProductRemoteDataSource)` | la abstracta `ProductRemoteDataSource` se resuelve a esta concreta |
| Repository (impl) | `@LazySingleton(as: ProductRepository)` | la abstracta `ProductRepository` se resuelve a esta concreta |
| UseCase | `@lazySingleton` | una instancia para toda la app |
| Servicio compartido | `@lazySingleton` | una instancia para toda la app |
| Cubit de pantalla | `@injectable` | `factory`: una instancia por request. **Nunca `@lazySingleton`** (un cubit singleton sobrevive al `dispose()` de su pantalla y fuga estado) |
| Cubit global (app-scope) | `@lazySingleton` | excepcion unica: cubit de ambito de app provisto una sola vez en `MultiBlocProvider` con `.value` (p. ej. `AuthCubit`) |
| Clases de terceros | `@module` | en `external_module.dart` |
| Entity, Model, interface de Repository, Params | — | **nunca** se anotan: son tipos de datos o contratos, no registros |

## Workflow — Modo `injectable`

1. Verificar que las clases del feature lleven su anotación. `clean-arch-feature` / `clean-arch-component` ya las emiten en los templates; si un componente vino sin ella (código previo o manual), añadirla.
2. Verificar `external_module.dart`: si el feature usa una librería externa no registrada (p. ej. `SupabaseClient`, `http.Client`), añadir su getter `@lazySingleton` al `@module`. Si `service_locator.dart` / `external_module.dart` no existen, crearlos desde cero.
3. Recordar al usuario que corra `make gen` (equivale a `dart run build_runner build --delete-conflicting-outputs`) para regenerar `service_locator.config.dart`.
4. Recordar que `service_locator.config.dart` **se commitea** y **nunca se edita a mano**: si al regenerar queda un diff, alguien anotó algo sin correr `make gen` (CI lo detecta con `git diff --exit-code -- '*.config.dart'`).
5. Recordar al usuario que debe: completar configuraciones, añadir imports faltantes, y verificar con análisis estático.

## Output — Modo `manual` (legacy / brownfield)

> ⚠️ **Solo brownfield.** Proyectos que ya tienen la cascada manual en `service_locator.dart` (v1) y aún no migraron a `injectable`. Para proyectos nuevos usa el modo `injectable`.

`lib/core/di/service_locator.dart` con cascada:

```dart
import 'package:get_it/get_it.dart';
import 'package:http/http.dart' as http;
import 'package:internet_connection_checker_plus/internet_connection_checker_plus.dart';
import 'package:isar_community/isar.dart';
import 'package:supabase_flutter/supabase_flutter.dart';
// ... imports de datasources, repositories, usecases, cubits
// import 'package:{app_name}/core/services/user_session.dart';
// import 'package:{app_name}/core/network/network_info.dart';

final GetIt sl = GetIt.instance;

Future<void> initDependencies() async {
  await IsarService.initialize();

  // ──────────────────────────────────────────────
  // External libraries
  // ──────────────────────────────────────────────
  sl
    ..registerLazySingleton<Isar>(() => IsarService.instance)
    ..registerLazySingleton<InternetConnection>(InternetConnection.createInstance)
    ..registerLazySingleton<http.Client>(http.Client.new);
  // `SupabaseClient` NO se registra: los datasources reciben
  // `Supabase.instance.client` directo en su constructor.

  // ──────────────────────────────────────────────
  // Core services
  // ──────────────────────────────────────────────
  sl
    ..registerLazySingleton<NetworkInfo>(() => NetworkInfoImpl(sl<InternetConnection>()))
    ..registerLazySingleton<UserSession>(() => UserSessionImpl(sl<Isar>(), supabase: Supabase.instance.client))
    ..registerLazySingleton<CacheManager>(CacheManager.new);

  // ──────────────────────────────────────────────
  // DataSources
  // ──────────────────────────────────────────────
  sl
    ..registerLazySingleton<ProductRemoteDataSource>(
      () => ProductRemoteDataSourceImpl(supabase: Supabase.instance.client),
    );

  // ──────────────────────────────────────────────
  // Repositories
  // ──────────────────────────────────────────────
  sl
    ..registerLazySingleton<ProductRepository>(
      () => ProductRepositoryImpl(
        remoteDataSource: sl<ProductRemoteDataSource>(),
      ),
    );

  // ──────────────────────────────────────────────
  // UseCases
  // ──────────────────────────────────────────────
  sl
    ..registerLazySingleton(() => GetProducts(sl()))
    ..registerLazySingleton(() => GetProduct(sl()))
    ..registerLazySingleton(() => CreateProduct(sl()))
    ..registerLazySingleton(() => DeleteProduct(sl()));

  // ──────────────────────────────────────────────
  // Cubits
  // ──────────────────────────────────────────────
  sl
    ..registerFactory(() => ProductCubit(
      getProducts: sl(),
      getProduct: sl(),
      createProduct: sl(),
      deleteProduct: sl(),
    ));
}
```

**Reglas del modo `manual`:**
- Orden de capas: external → core → datasources → repositories → usecases → cubits.
- `registerLazySingleton` para todo excepto Cubits (`registerFactory`).
- `SupabaseClient` NO se registra; los datasources lo inyectan como `Supabase.instance.client` en el constructor.
- Si `service_locator.dart` no existe, crearlo desde cero; si existe, añadir los nuevos registros en la sección correspondiente.
- Los bodies de configuración van con `throw UnimplementedError()` o `// TODO: configure`.

## Workflow general

1. Preguntar al usuario: mode (default `injectable`), app_name, lista de features con sus dependencias, y librerías externas si aplican.
2. En modo `injectable`: seguir el [Workflow — Modo injectable](#workflow--modo-injectable).
3. En modo `manual`: seguir las reglas del modo manual (crear/actualizar `service_locator.dart` con la cascada).
4. No generar bodies de métodos — usar `throw UnimplementedError()`.
5. Recordar al usuario que debe: completar configuraciones, añadir imports faltantes, correr `make gen` (injectable) y verificar con análisis estático.
