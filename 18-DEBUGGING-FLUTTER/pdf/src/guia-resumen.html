Modos de ejecución y fundamentos

debug · profile · release
ModoPara quéOptimizaciones
debugDepurar con breakpoints, hot reloadNinguna (lento)
profileMedir rendimiento (siempre aquí)Mayoría habilitadas
releasePublicar, verificar buildsTodas

Regla de oro: para debugging usa debug; para medir performance usa profile — nunca midas en debug (el JIT distorsiona todo). Flag clave: --dart-define para config por entorno y --start-paused para esperar al debugger.

1

launch.json y breakpoints

F5 · logpoints · conditionals

launch.json define configuraciones reutilizables: nombre, programa, --dart-define, device, args. Con una configuración flutter attach puedes conectar el debugger a un app ya corriendo (sin --debug-port).

BreakpointUso
NormalPausa la ejecución en una línea
ConditionalPausa solo si la condición es true
LogpointImprime en Debug Console sin pausar (reemplaza print())
FunctionPausa al entrar a una función

Regla: usa logpoints en lugar de print() para debugging temporal — no contaminan el código y se pueden dejar activos sin pausar la app.

2

Inspección de datos y Debug Console

VARIABLES · WATCH · REPL
  • VARIABLES: valores de las variables locales durante el pause.
  • WATCH: expresiones que se reevalúan en cada pause (ej. user.name, items.length).
  • Debug Console = REPL: ejecuta código Dart en el contexto actual de la sesión (crear objetos, llamar métodos).
  • Multi-target: launch.json con configuraciones por device (android, ios, chrome) y debugging remoto por red.

Flujo típico: breakpoint → inspeccionar VARIABLES → evaluar expresiones en Debug Console → avanzar con F10/F11/F5 (Step Over/Into/Continue).

Fundamentos de Flutter DevTools

dart devtools · vistas

DevTools es la suite de profiling y diagnóstico de Flutter. Se abre con dart devtools <vm-service-uri> (URI posicional del VM Service) o desde VS Code con el comando Dart: Open DevTools.

VistaPara qué
Flutter InspectorWidget tree, layout, constraints
PerformanceFrames, jank, flame chart
MemoryHeap, leaks, GC, snapshots
CPU ProfilerFlame chart por sampling
NetworkRequests HTTP y WebSocket
DebuggerBreakpoints sincronizados con VS Code
LoggingLogs de package:logging y print
App SizeAnálisis del tamaño del build

Configuración: dart.devToolsTheme y dart.devToolsBrowser en settings de VS Code. El Debugger de DevTools comparte el mismo VM Service que VS Code: los breakpoints se sincronizan automáticamente.

4

Flutter Inspector y Performance

widget tree · frames · jank

Flutter Inspector: explora el widget tree, selecciona widgets, inspecciona propiedades y constraints. Usa Select Widget Mode para encontrar dónde se ve mal un widget. MediaQuery responsive: MediaQuery.sizeOf(context).

Performance View: graba el timeline y muestra cada frame. Un frame debe completarse en <16.6ms (60fps).

SeñalSignificado
Frame rojoUI thread lento (build/layout)
Frame moradoRaster thread lento (paint/compositing)
Build time > 8msRebuilds excesivos en listas
Enhance TracingWidget rebuilds por elemento

Diagnóstico: graba 5-10 segundos de interacción → identifica el frame más lento → analiza el flame chart → clasifica (build vs raster).

5

CPU Profiler y Memory View

sampling · heap · GC

CPU Profiler: muestrea la CPU (sample rate por defecto) y genera un flame chart: qué función consume más tiempo de ejecución.

MemoriaUso
Take Heap SnapshotEstado de la memoria en un momento
Diff SnapshotCompara dos momentos → detecta clases que crecen
GCColecciones de basura del isolate

Detectar leaks: snapshot base → navegar 5-10 veces a la pantalla sospechosa → diff snapshot → buscar StreamSubscription, TextEditingController, Timer, AnimationController que crecen → fix: cancelar/cerrar en dispose().

6

Network, Logging y Debugger View

requests · niveles · logpoints
  • Network: lista requests HTTP/WebSocket, ver body, headers y status code. Útil para APIs (Supabase, dio). Copia como cURL para probar fuera.
  • Logging: interpreta niveles de package:logging (FINE, INFO, WARNING, SEVERE, SHOUT) + prints. Filtros por nivel mínimo, texto y tag.
  • Debugger View: alternativa de DevTools al debugging de VS Code: pausa, variables, call stack y logpoints, todo en el navegador.

Recomendación: Network View para debugging de API, Debug Console para lógica, Logging para trazas largas. Para debugging extensivo, VS Code es más rápido en el día a día.

App Size: reducir el tamaño del build

analyze-size · límites de stores 
flutter build apk --analyze-size
flutter build appbundle --analyze-size
flutter build ios --analyze-size
  • Google Play: límite 200 MB para AAB.
  • App Store: 2 GB binario; >200 MB no descargable por datos móviles.
  • Deferred imports para código pesado (solo web).
  • Mayores culpables: assets sin comprimir, imágenes enormes, dependencias no usadas (usa flutter pub deps y remueve).

Pipeline: --analyze-size genera un reporte visual en Chrome DevTools App Size → identificar el paquete/asset dominante → optimizar (imágenes, shrink, --split-debug-info).

8

Rendimiento: rebuilds, const y RepaintBoundary

build · paint · 60fps

Cada frame tiene 2 fases: build/layout (UI thread) y paint/raster (raster thread). El objetivo: mantener ambas < 8ms.

TécnicaEfecto
constWidgets estáticos no se reconstruyen (reducción del 50-80% en UIs estáticas)
ListView.builderSolo construye items visibles
BlocSelector / buildWhenRebuilds selectivos del subtree
RepaintBoundaryAísla el repintado (animaciones en listas)
shouldRepaintCustomPainter solo repinta si cambia
Extraer widgetsCada widget se reconstruye de forma independiente

Regla: solo optimiza donde tengas un problema medible en profile mode. Agregar RepaintBoundary incorrectamente puede empeorar el rendimiento.

9

Memory leaks y rendering complejo

dispose · slivers · imágenes

Patrones de leak (y su fix)

  • StreamSubscription → guardar referencia y cancel() en dispose().
  • TextEditingController / ScrollController → dispose() (y removeListener).
  • Timer.periodic → cancel() en dispose().
  • setState después de await → if (!mounted) return.

Rendering complejo

  • ListView.builder vs ListView: lazily built siempre para >20 items.
  • CustomScrollView + Slivers para layouts de scroll complejos; SliverFixedExtentList si el alto es fijo.
  • Imágenes: cacheWidth/cacheHeight según el tamaño de display + precacheImage.
  • Evita Opacity sobre subtrees grandes; usa AnimatedOpacity o IgnorePointer.

Memoria por imagen: 4000×3000 = 48 MB sin cacheWidth; con redimensión a 200×150 ≈ 120 KB. La diferencia es ~400×.

Debugging asíncrono y workflow por tipo de bug

futures · streams · event loop

Los 5 bugs asíncronos: Future que nunca completa (falta try/catch) · setState sin mounted check · llamadas secuenciales innecesarias (usa Future.wait) · stream sin cancelar · Completer manual innecesario.

Patrón de carga segura: try/catch alrededor del await + estado de loading/error/data + timeout (fetch().timeout(...)) + trabajo pesado delegado a compute() para no bloquear el UI thread.

Tipo de bugHerramienta principal
UI se ve malFlutter Inspector → Select Widget
Estado inconsistentePrints + Bloc Inspector
App lentaPerformance View (frames >16ms)
API fallaNetwork View + cURL
Memory leakMemory View → diff snapshots
Build errorLeer el error completo
Hot Reload no funcionaHot Restart (no recarga initState/main/imports)

Framework general: REPRODUCIR → AISLAR → DIAGNOSTICAR → CORREGIR → VERIFICAR.

Debugging por capa: ejecución aislada con el debugger

modo andamiaje SDD · scratchpad · real vs stub

Cuando desarrollas una feature en modo andamiaje SDD (los cuerpos empiezan con throw UnimplementedError()), la feature no está cableada y no puedes verla desde la app completa. La técnica: crear un scratchpad (tool/scratch/main_<capa>.dart), correrlo con el debugger (F5) y verificar cada capa aislada a medida que la implementas — sin tests obligatorios ni dependencia de la IA.

Dos modos de verificación:

ModoCuándoQué verificas
A · Real (integración)Capas de datos (datasource → Supabase, repository → datasource)Respuesta real de la API, excepciones reales, request en Network View
B · Aislado con stubCapas superiores (usecase, cubit) cuando la dependencia inferior no está listaLógica de la capa con un stub manual (Either<Failure,T>, transiciones de estado)
CapaRuntimeModoQué verificas
Entity / Model / Statedart run—Cálculos puros, roundtrip JSON, invariantes, Equatable/copyWith/props
UseCasedart runB stubEither<Failure,T> + mensajes exactos de validación
DataSourceflutter run -tA realRespuesta JSON real, AuthException/SocketException, RPC
RepositoryImplflutter run -tA o BMapeo excepción → Failure, delega al datasource
Cubitflutter run -tB stubTransiciones de estado (BlocObserver + Bloc Inspector)
Page/Widgetflutter runA o B + InspectorRender por cada estado (Loading/Loaded/Error)

Regla: inyecta dependencias a mano en el scratchpad, sin GetIt. Entra cada scratchpad en launch.json (agrúpalos con presentation). Secuencia: Entity → Model → DataSource → State → Repository → UseCase → Cubit → Page → Wiring. Verifica cada capa en cuanto la terminas, antes de construir la siguiente. Capas puras (entity/model/usecase/state) → dart run; capas con Flutter (datasource/cubit/page) → flutter run -t.
