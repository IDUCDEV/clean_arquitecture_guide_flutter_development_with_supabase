Modos de ejecución y fundamentos

debug · profile · release · hot reload

Todo el módulo arranca de elegir el modo correcto: el debugger y DevTools viven en debug/profile; la medición de rendimiento solo vale en profile (en debug el JIT no optimiza, 10-100× más lento y con asserts activados). Un frame pasa por UI thread (build → layout → paint, código Dart/BLoC) y Raster thread (pintado GPU; la compilación de shaders es fuente típica de jank).

ModoPara quéOptimizaciones
debugDepurar con breakpoints, hot reloadNinguna (lento)
profileMedir rendimiento (siempre aquí)Mayoría habilitadas
releasePublicar, verificar buildsTodas

Hot Reload vs Hot Restart

Hot Reload (r)Hot Restart (R / Ctrl+Shift+F5)
EstadoConserva (BLoC, scroll, controllers, breakpoints)Reinicia todo (vuelve a initState()), limpia breakpoints
CuándoCambios visuales en build()initState(), main(), const, imports, static fields, config
Duración~1-2 s~5-10 s

Regla de oro: para debugging usa debug; para medir performance usa profile — nunca midas en debug (el JIT distorsiona todo). Flag clave: --dart-define para config por entorno y --start-paused para esperar al debugger.

launch.json y breakpoints avanzados

F5 · logpoints · condicionales · attach

launch.json (.vscode/launch.json) define configuraciones reutilizables: comando, plataforma, args y attach. Con "request": "attach" el debugger se conecta a una app ya corriendo sin copiar la URI (solo en debug/profile; release no expone VM Service).

ClaveUso
requestlaunch | attach
programlib/main.dart (o test/x_test.dart)
flutterModedebug · profile · release (preferir a toolArgs)
dartDefine["KEY=value"] → --dart-define (config por entorno)
toolArgsArgs de flutter run: -d device, --flavor, -t entrypoint
argsArgs del programa/test, ej. --name "login exitoso"
compoundsLanzar varias configuraciones a la vez (app + worker isolate)

Los 8 tipos de breakpoint

TipoPausaUso
NormalSíPausa en una línea (F9)
CondicionalSíSolo si la condición es true: state is LoginError, items.length > 100
Hit CountSíTras N hit: == 1, > 10 (ej. frame 30 de una animación)
TriggeredSíSe dispara cuando otro breakpoint se activó antes
InlineSíColumna exacta de una línea (Ctrl+Shift+F9 en sesión)
FunctionSíPor nombre: setState, Navigator.push (fallback: línea)
DataSoporte limitadoCuando el valor de una variable cambia
LogpointNo"Email: {event.email}" logea sin pausar (diamante azul)

Regla: usa logpoints en lugar de print() para debugging temporal — no contaminan el código, pueden ser condicionales y no se commitean. Seguridad: nunca pongas anon keys/secretos en launch.json; usa String.fromEnvironment desde .env o variables del sistema.

Inspección de datos y Debug Console

VARIABLES · WATCH · REPL
  • VARIABLES: valores locales durante el pause. Copy as Expression (pega en WATCH) y Set Value te permiten simular edge cases (ej. event.email = "") sin tocar código.
  • WATCH: expresiones Dart reevaluadas en cada pause.
  • Debug Console = REPL (Ctrl+Shift+Y): ejecuta código en el contexto de la sesión — crear objetos, await, modificar variables, multiline con Shift+Enter.
  • Multi-target: config por device (android, ios, chrome) y debugging remoto por red (adb connect, --web-port).

Fundamentos de Flutter DevTools

vm service · vistas · limitaciones

DevTools es la suite de profiling y diagnóstico de Flutter (no un debugger). Conecta con la app vía VM Service (socket sobre DDS). Cómo abrirla: pulsa d en el terminal de flutter run, o Ctrl+Shift+P → Dart: Open DevTools, o dart devtools <vm-service-uri>. Solo funciona en --debug/--profile, nunca en release.

VistaPara qué
Flutter InspectorWidget tree, layout, constraints
PerformanceFrames, jank, flame chart
MemoryHeap, leaks, GC, snapshots
CPU ProfilerFlame chart por sampling
NetworkRequests HTTP y WebSocket
DebuggerBreakpoints sincronizados con VS Code
LoggingLogs de package:logging y print
App SizeAnálisis del tamaño del build

Limitaciones: Network solo ve requests hechos desde Dart (los nativos quedan invisibles); los snapshots de memoria son aproximados en debug; debug mode añade overhead de rendimiento. El Debugger de DevTools comparte VM Service con VS Code: los breakpoints se sincronizan solos.

Flutter Inspector y Performance

layout explorer · frames · budgets

Flutter Inspector: Widget Tree / Details / Layout Explorer (distingue constraints impuestas por el padre vs tamaño real, p.ej. 0 ≤ w ≤ 411, 0 ≤ h ≤ ∞). Select Widget Mode localiza en la app el widget que se ve mal. MediaQuery responsive: MediaQuery.sizeOf(context).

Debug Paint 🎨Significado
AzulBounds del widget
AmarilloPadding / margin
VerdeOverflow (→ Wrap, SingleChildScrollView, maxLines+ellipsis)
RojoError de layout / constraints inválidas
  • Widget no aparece: ¿existe en el tree? (si no, es bug de lógica)
  • ¿width: 0 / height: 0 por constraints?
  • ¿Overflow? → Wrap / maxLines + TextOverflow.ellipsis

Performance View: graba el timeline; cada frame debe completarse en <16.67 ms (60fps) / <8.33 ms (120fps). Frame verde = OK, rojo = UI thread lento (build/layout), morado = raster thread lento (paint/compositing).

Threshold (Frame Analysis)Si se supera
Widget rebuilds < 100 / frameUsar const, extraer widgets
Layout / paint < 5 msSimplificar árbol, RepaintBoundary
Build > 8 ms en listasListView.builder
Shaders compilando cada frameImpeller (default 3.10+); precache en web
Isolate bloqueadocompute() / isolate
Presión de GCMenos alocaciones por frame

Diagnóstico: graba 5-10 segundos de interacción en --profile → identifica el frame más lento → flame chart → clasifica (build vs raster) → aplica el fix de la fila.

CPU Profiler y Memory View

sampling · retained · snapshots

CPU Profiler: muestrea la CPU y genera flame chart. Self time = solo esa función; Total time = función + hijos. Bottom Up ordena por self time para encontrar las funciones calientes.

Señal CPUFix
Trabajo caro en build()Hoist a initState con late final
Image.network re-descargacacheWidth: 500 / cached_network_image
TextPainter dominamaxLines + ellipsis / ConstrainedBox
AnimatedBuilder rebuilda todoPasar un child: estable (se builda una vez)

Memory View: categorías Dart Heap (objetos Dart), External (nativo, imágenes), GPU. En los snapshots, ordena por Retained Size (objeto + todo lo que referencia) vs Shallow Size (objeto solo) vs Instances.

OperaciónUso
Take Heap SnapshotEstado de la memoria en un momento
Diff SnapshotBase → navegar a la pantalla 5-10× → comparar; clases que crecen = leak
TraceClase concreta: Allocations > Deallocations de forma estable = leak
GCColecciones de basura del isolate

Detectar leaks: snapshot base → navegar 5-10 veces a la pantalla sospechosa → diff snapshot → buscar StreamSubscription, TextEditingController, Timer, AnimationController que crecen → fix: cancelar/cerrar en dispose().

Network, Logging y Debugger View

filtros · staging · niveles
  • Network: lista requests HTTP/WebSocket con body, headers y status. Verde 200-299, ámbar 300-399, rojo 400-599. Copia como cURL para probar fuera.
  • Timing de cada request: DNS → TCP → TLS → Waiting → Response. DNS alto → cache DNS/IP; Waiting alto → backend/RLS/índices; Response alto → paginación/compresión.
  • Logging: interpreta niveles de package:logging: FINE (verbose, gris) · INFO (azul) · WARNING (amarillo) · SEVERE (rojo) · SHOUT (fatal). Filtros por nivel mínimo, texto y tag.
  • Debugger View: debugger web con el mismo VM Service: pausa, variables, call stack y logpoints sincronizados con VS Code.
// Sintaxis de filtros de Network
method:GET  status:200  url:products
status:4xx          # todos los client errors
-type:image         # exclusión
method:POST status:200        # combinables

// Tags para filtrar Logging
debugPrint('[AUTH] ...') / '[API]' / '[BLOC]' / '[PRODUCTS]'
// Filtro: message:AUTH · Logging condicional: if (kDebugMode)

Recomendación: Network View para debugging de API (debugPrint del resultado + Rows: ${data.length}), Debug Console para lógica, Logging para trazas largas. debugPrint auto-throttle la salida en debug — prefírela a print().

Rendimiento: rebuilds, keys y const

build · paint · selectors · 60fps

El build()/setState() del padre rebuilda todos los descendientes. Objetivo: mantener build y raster < 8 ms (ideal < 4).

TécnicaEfecto
constReusa la misma instancia → no hay build del subtree (50-80% menos rebuilds en UIs estáticas)
ListView.builderSolo construye items visibles
BlocSelector / buildWhenRebuilds selectivos del subtree según campo/condición
RepaintBoundaryAísla el repintado (animaciones en listas)
shouldRepaintCustomPainter solo repinta si cambia (false si estático)
Extraer widgetsCada widget se reconstruye de forma independiente (const ExpensiveChild)

Keys

KeyCuándo
ValueKey(item.id)Listas dinámicas con id único — sin ella Flutter mezcla items al reordenar
ObjectKeyIdentidad de objeto (objetos que no usan ==)
UniqueKeyForzar recreación completa del widget
GlobalKeyAcceder a estado desde fuera (forms, navegación)
NingunaKey sin motivo = overhead: solo úsala cuando Flutter necesita distinguir widgets

Anti-patterns de setState

  • setState en loop → agrupa todas las mutaciones en un setState.
  • setState en didChangeDependencies → puede reconstruir infinitamente; carga en initState + async.
  • setState vacío sin cambio real.
  • Mutar una colección: _items.add(...) no notifica → usa nueva referencia _items = [..._items, item].

Regla: solo optimiza donde tengas un problema medible en profile mode. BlocSelector = un campo; buildWhen = varias condiciones. Agregar RepaintBoundary incorrectamente puede empeorar el rendimiento. Medir en debug no vale.

Memory leaks y rendering complejo

dispose · slivers · imágenes

Patrones de leak (y su fix)

LeakFix
StreamSubscription sin cancelar_subscription?.cancel() en dispose() (BLoC: en close())
TextEditingController / ScrollControllerremoveListener antes de dispose()
Timer.periodic sin cancelar_timer.cancel() en dispose()
Closure capturando contextGuard if (mounted) / flag _isDisposed
setState tras awaitif (!mounted) return después de cada await
Listener no removidoaddObserver/removeObserver simétricos
 
// Orden correcto en dispose()
_subscription?.cancel();
_animController.dispose();
_scrollController.removeListener(_onScroll);
_scrollController.dispose();
_textController.dispose();
super.dispose();   // siempre al final

Regla de oro: "Si creaste un controller o te suscribiste a un stream, DEBES cerrarlo en dispose()". Monitoriza con un BlocObserver (onCreate/onClose/onError) + diff snapshot para confirmar.

Rendering complejo

  • >50 items → ListView.builder obligatorio (O(1) vs O(n) de ListView). Alto fijo → SliverFixedExtentList/SliverPrototypeExtentList.
  • Imágenes: cacheWidth/cacheHeight = (width * devicePixelRatio).toInt() + precacheImage en initState.
  • Opacity = "villano silencioso" (crea capa de composición): evítalo sobre subtrees grandes; usa AnimatedOpacity/IgnorePointer. BackdropFilter = coste muy alto. Prefiere Decoration con borderRadius sobre ClipRRect.

Memoria por imagen: 4000×3000 = 48 MB sin cacheWidth; con redimensión a 200×150 ≈ 120 KB — la diferencia es ~400×.

Debugging asíncrono (25)

futures · streams · event loop

Aproximadamente el 80% de los bugs difíciles de Flutter son asíncronos. Orden del event loop: síncrono → microtasks (Future.microtask) → timers (Future.delayed).

BugFix
Future que nunca completa → loading infinitotry/catch en el await + reset en catch
setState tras desmontar → crashif (!mounted) return tras cada await
Llamadas secuenciales → lentaFuture.wait([fetchUsers(), fetchPosts()])
Stream sin cancelar → leak_subscription.cancel() en dispose()
Completer manual innecesariofinal result = await fetch();
Trabajo pesado bloqueando el framecompute(_computeSum, 10_000_000)
 
// Timeout SIEMPRE en red
fetch().timeout(10s, onTimeout: () => throw TimeoutException('...'));
posts.first.timeout(5s, onTimeout: () => throw TimeoutException('...'));

// Detectar streams silenciosos: wrapped en función con Stopwatch + logs

Patrón de carga segura: try/catch alrededor del await + estado loading/error/data + timeout + trabajo pesado delegado a compute() para no bloquear el UI thread.

Mentalidad de debugging (27)

no adivines · observa · anti-IA

Debuggear es una mentalidad, no una herramienta. "No adivines, observa": la evidencia está en los datos, no en tu intuición ni en la IA. La IA acelera fixes solo cuando ya entiendes el bug.

Las 3 reglasEn la práctica
1. Nunca supongas, verifica"Creo que es un null" → inspecciona la variable; "el estado no cambia" → breakpoint en emit; "hay un rebuild innecesario" → debugPrintRebuildDirtyWidgets
2. Reduce el espacio de búsquedaBinary search: divide el flujo por la mitad en cada paso (~log2(100) = 7 iteraciones para 100 archivos)
3. Reproduce antes de arreglarSi no puedes reproducirlo, no puedes arreglarlo
Usar IA ✅No usar IA ❌
Sintaxis de un bug ya entendidoNo sabes POR QUÉ falla
Boilerplate (p.ej. interceptor HTTP)Lógica de negocio
Aprender patrones/paquetesUn fix que solo "parece funcionar"
Explicar errores de compilaciónPerformance/memoria (la IA no puede medir)
Entender el call stack completo (le falta el estado runtime)

Test de la dependencia: "¿Podrías explicarle a otro developer exactamente qué está pasando y por qué?" Si NO → aún no entiendes el bug. Y para pedir ayuda (humana o de IA), el checklist del §14 te dice si ya hiciste lo tuyo.

Playbook de debugging sistemático (29)

6 pasos · sin IA · imprímelo

Un paso-a-paso reproducible para diagnosticar CUALQUIER bug sin pedir ayuda a la IA. Imprime esta sección y tenla al lado del monitor.

1ENTENDER¿Qué se esperaba vs qué pasó? 2REPRODUCIRSteps exactos, siempre falla 3AISLARBinary search con breakpoints
4DIAGNOSTICARDatos, call stack, watch 5CORREGIRFix mínimo, un cambio a la vez 6VERIFICARReproducir + tests + regresión

Paso 1 — ENTENDER

Responde por escrito las 7 preguntas (notepad, doc o comment):

  • ¿Qué behavior esperaba ver?
  • ¿Qué behavior veo en realidad?
  • ¿Cuándo empezó a pasar? (¿antes funcionaba?)
  • ¿Pasa siempre o solo a veces?
  • ¿En qué dispositivo/plataforma?
  • ¿Con qué datos de entrada?
  • ¿Cambié algo recientemente? (git log --oneline -10)

Si no puedes responder la #1 → el bug no es técnico, es de requirements: habla con tu team/product owner antes de debuggear.

# Git como herramienta de debugging
git log --oneline -10
git diff HEAD~5 lib/presentation/bloc/login/login_bloc.dart
git stash && git checkout <hash>   # probar si funcionaba antes
git checkout - && git stash pop    # volver a HEAD y recuperar

Paso 2 — REPRODUCIR

Escribe los steps exactos con la acción OBSERVAR final:

1. Abrir la app → 2. Ir a login → 3. Escribir "test@email.com"
4. Escribir "12345678" → 5. Presionar "Login"
6. OBSERVAR: loading infinito
¿Cuándo falla?Qué hacer
Con datos específicosProbar con esos datos exactos
Después de cierto tiempoEsperar ese tiempo
En cierto orden de accionesRepetir el orden exacto
Con cierto estado previoForzar ese estado primero

Si no reproduces: logging detallado (debugPrint) en el flujo sospechoso · mismo entorno (dispositivo+OS) · reports de usuarios: ¿qué tienen en común? · DevTools → Logging en background.

Paso 3 — AISLAR (Binary Search Debugging)

En vez de leer 50 archivos, pon un breakpoint en la mitad del flujo: si el estado es correcto hasta ahí → el bug está después; si ya es incorrecto → está antes. En 3-4 iteraciones encuentras el paso exacto.

LoginSubmitted → validate → LoginUseCase → repository → api → emit(result)
Breakpoint 2 (validate): datos válidos ✓
Breakpoint 4 (repository): resultado Left(failure) ✗
→ el bug está entre el UseCase y el repository
CapaQué inspeccionar en el breakpoint
Eventoevent.email, event.password
ValidateResultado, errores
UseCaseparams que recibe, result que retorna
RepositoryDatos que envía, respuesta que recibe
API / DatasourceRequest body, response, status code, headers
Statestate.runtimeType, campos emitidos

Paso 4 — DIAGNOSTICAR

Herramientas en orden:

  1. VARIABLES → ¿qué valor tiene la variable sospechosa?
  2. WATCH → state.runtimeType, result.runtimeType
  3. CALL STACK → ¿cómo llegué aquí?
  4. Debug Console → probar "what if", await
  5. debugPrint() → logging para el siguiente paso
// Expresiones para WATCH
state.runtimeType
result.runtimeType == Left<Failure, User>
myMap.keys.toList()
myList.length / myList.first / myList.isEmpty

Paso 5 — CORREGIR

ReglaTipo de bugFix típico
1 cambio a la vez · fix mínimo · sin features · commit tras el fixNull safety? o ?? default
Estado no se actualizaVerificar que emit() se ejecuta
Widget no se veConstraints, Expanded/Flexible

Paso 6 — VERIFICAR

  • Reproducir los steps del Paso 2: ¿el bug ya no aparece?
  • ¿Todos los tests existentes pasan?
  • Probar el happy path completo + edge cases (vacío, límites)
  • Probar en otro dispositivo/emulador (¿es específico de plataforma?)
  • ¿Sin regresiones en funcionalidad relacionada?

Si algo se rompió: revierte el fix (git checkout <archivo>) → vuelve al Paso 3 → busca una solución que no rompa lo existente (o agrega un test que cubra el caso roto).

15 preguntas ANTES de pedir ayuda

  • ¿Puedo reproducir el bug consistentemente?
  • ¿Sé exactamente qué pasos lo provocan?
  • ¿En qué archivo/función ocurre?
  • ¿Qué valor tiene la variable sospechosa al fallar?
  • ¿Qué dice el call stack?
  • ¿Qué cambió recientemente? (git log)
  • ¿Es de compilación o de runtime?
  • ¿Es nuevo o existente?
  • ¿Puse un breakpoint en el lugar correcto?
  • ¿Inspeccioné con WATCH / Debug Console?
  • ¿Leí el error COMPLETO?
  • ¿Busqué en Google/Stack Overflow?
  • ¿Revisé la documentación oficial del package/API?
  • ¿Puedo explicárselo a otro developer?
  • ¿Entiendo QUÉ falla (no solo CÓMO arreglarlo)?

Regla: >3 casillas sin marcar → estás pidiendo ayuda demasiado pronto. La respuesta está en los datos, no en tu intuición.

Debugging por capa: ejecución aislada con el debugger

modo andamiaje SDD · scratchpad · real vs stub

Cuando desarrollas una feature en modo andamiaje SDD (los cuerpos empiezan con throw UnimplementedError()), la feature no está cableada y no puedes verla desde la app completa. La técnica: crear un scratchpad (tool/scratch/main_<capa>.dart), correrlo con el debugger (F5) y verificar cada capa aislada a medida que la implementas — sin tests obligatorios ni dependencia de la IA.

Dos modos de verificación:

ModoCuándoQué verificas
A · Real (integración)Capas de datos (datasource → Supabase, repository → datasource)Respuesta real de la API, excepciones reales, request en Network View
B · Aislado con stubCapas superiores (usecase, cubit) cuando la dependencia inferior no está listaLógica de la capa con un stub manual (Either<Failure,T>, transiciones de estado)
CapaRuntimeModoQué verificas
Entity / Model / Statedart run—Cálculos puros, roundtrip JSON, invariantes, Equatable/copyWith/props
UseCasedart runB stubEither<Failure,T> + mensajes exactos de validación
DataSourceflutter run -tA realRespuesta JSON real, AuthException/SocketException, RPC
RepositoryImplflutter run -tA o BMapeo excepción → Failure, delega al datasource
Cubitflutter run -tB stubTransiciones de estado (BlocObserver + Bloc Inspector)
Page/Widgetflutter runA o B + InspectorRender por cada estado (Loading/Loaded/Error)

Regla: inyecta dependencias a mano en el scratchpad, sin GetIt. Entra cada scratchpad en launch.json (agrúpalos con presentation). Secuencia: Entity → Model → DataSource → State → Repository → UseCase → Cubit → Page → Wiring. Verifica cada capa en cuanto la terminas. Capas puras → dart run; capas con Flutter → flutter run -t.

Prácticas, cheatsheets y métricas

escenarios reales · atajos · ideales

Resultados reales de los escenarios (07, 18, 24)

  • Lista de 10.000 items → ListView.builder: frame medio 125→12 ms, build 45→3 ms, memoria ~80→~15 MB.
  • Checkout con 4 bugs → Inspector→Wrap · Network→Future.wait · Memory→dispose() · CPU→RepaintBoundary/ValueListenableBuilder.
  • API secuencial (perfil) 3 llamadas 2900 ms → Future.wait → 1200 ms (-59%).

  • Login parpadeante → BlocSelector: 15→3 rebuilds/tecla, 12→1 ms.
